## F1 — `probes` is two higher than the number of probes run (Medium)

**Claim:** the markdown report says "Probes: N", and
`references/report-format.md` documents `probes` as the number of probes.
**Evidence:** a six-commit repository bisected with
`--good HEAD~5 --bad HEAD --cmd 'test "$(cat n.txt)" -lt 4'` reported
`probes: 5` with `steps` `[bad, good, good, bad, bad]`. The raw log:

```
# bad: [8b46f1b] c6
# good: [3ad0006] c1
git bisect start 'HEAD' 'HEAD~5'
# good: [070efa2] c3
# bad: [871112b] c5
# bad: [639864e] c4
# first bad commit: [639864e] c4
```

Three probes ran. The first two `#` lines are the range endpoints, which
`parse_bisect_log` treated as probes. The README capture showed the same defect:
`docs/regression-hunt.svg` said "4 probes" for the demo's two-probe run.
**Cause:** `probes = len(steps)`, and `steps` includes the endpoint lines.
**Fix:** `parse_bisect_log` marks entries before the `git bisect start` line as
`endpoint: true`; `probes` counts only `endpoint: false`; the markdown table
lists only real probes, since the endpoints are already in the header.
`report-format.md` documents both. `docs/` regenerated from the fixed run.
**Status:** fixed. `test_marks_the_endpoint_lines_and_counts_only_probes` covers
the parser; `test_json_report_has_the_documented_schema` now asserts
`probes == steps without endpoints` and exactly two endpoints, where it
previously asserted only `probes >= 1`.
